1. O PROBLEMA QUE EXISTIA ANTES
================================================================================

O formato do banco (as tabelas, colunas, tipos) era guardado num arquivo .txt
chamado SQL_CREATE_TABLES.txt, com SQL escrito a mao.

Para instalar num banco novo, o caminho era:
    1. abrir o Supabase
    2. abrir o SQL Editor
    3. copiar o SQL do .txt
    4. colar e rodar
    5. torcer para nao ter erro de digitacao

Problemas desse jeito:
  - Se voce esquecesse de uma coluna, o app quebrava so depois, com uma
    mensagem confusa do tipo "column does not exist".
  - O arquivo ficou desatualizado de verdade: faltava a coluna usuario_id,
    que e a que separa os dados de cada usuario no app. Quem copiasse aquele
    .txt num banco novo ficaria com um banco incompleto.
  - Nao tinha como saber o que mudou, nem quando, nem por que.
  - Em outra maquina, tinha que repetir o trabalho do zero.


2. O QUE E O ALEMBIC
================================================================================

E uma ferramenta que guarda o formato do banco DENTRO DO PROJETO, em codigo,
e aplica as mudancas no banco com um comando.

Em vez de um .txt com SQL solto, o schema passa a ter duas fontes:

    database/models.py        -> como as tabelas sao (a verdade final)
    migrations/versions/*.py  -> o historico do que ja foi aplicado

O Alembic tambem grava no proprio banco uma tabelinha chamada
alembic_version, dizendo em qual revisao aquele banco esta. E por isso que ele
sabe o que ainda falta aplicar: se voce rodar de novo sem mudanca nenhuma,
ele nao faz nada (nao duplica tabela, nao apaga dado).

Importante: ele cuida so do FORMATO do banco (tabelas, colunas, indices).
Os DADOS (as linhas: pacientes, consultas, orcamentos) sao do app. Alembic
nao cadastra, nao apaga e nao copia registro nenhum.


2.1 COMO ELE FUNCIONA POR DENTRO
================================================================================

A duvida mais comum: "ele monta um SQL e manda pro banco?"

Quase isso. O arquivo de migration NAO contem SQL escrito. Ele contem CHAMADAS
Python que descrevem o que deve mudar. Exemplo real do 0001_baseline.py:

    op.create_table(
        "Consultas",
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("valor", sa.Numeric(precision=10, scale=2)),
        sa.Column("duracao", sa.Integer(), server_default="30", nullable=False),
    )

Repare que nao existe CREATE TABLE escrito ali. O texto SQL que chega no
Supabase e montado na hora, pelo SQLAlchemy, usando o dialeto do Postgres.

O caminho completo de um comando:

    alembic upgrade head
      |
      +- 1. le o alembic.ini e acha a pasta migrations/
      |
      +- 2. carrega o migrations/env.py
      |     |- pega a URL do banco no .env (via database/connection.py)
      |     |- abre UMA conexao com o Supabase
      |
      +- 3. pergunta ao banco: "em qual revisao voce esta?"
      |     +- SELECT version_num FROM alembic_version
      |
      +- 4. descobre o caminho da revisao atual ate a "head"
      |     +- le o arquivo .py da proxima revisao e chama upgrade()
      |
      +- 5. dentro de upgrade(), cada op.create_table() vira um objeto DDL
      |
      +- 6. o SQLAlchemy traduz esse objeto para SQL do Postgres
      |     +- e aqui que sa.Integer() vira SERIAL
      |
      +- 7. o driver pg8000 envia o texto para o Supabase
            +- BEGIN;  ... comandos ...  COMMIT;

A prova de que o SQL e gerado, e nao escrito: o arquivo pede
sa.Column("id", sa.Integer()) e o Postgres recebeu "id SERIAL NOT NULL".
O SQLAlchemy fez essa troca. O mesmo arquivo em outro banco geraria outra
coisa:

    PostgreSQL   ->  SERIAL
    SQLite       ->  INTEGER + AUTOINCREMENT
    SQL Server   ->  INT IDENTITY

E por isso que a migration e codigo e nao texto: ela sabe se adaptar ao banco.
Um .txt com SERIAL colado no Supabase quebraria se voce trocasse de
fornecedor. (Este projeto tambem roda os testes em SQLite, aproveitando
exatamente essa adaptability - veja os 146 testes.)

ONDE EXISTE SQL ESCRITO A MAO
Existe um lugar so, e por necessidade: a revisao 0002_rls.py usa op.execute().

    op.execute(f'ALTER TABLE "{tabela}" ENABLE ROW LEVEL SECURITY')

O RLS (seguranca de linha) nao tem representacao no SQLAlchemy - nao existe
"construtor" para ele. Entao ali o Alembic e obrigado a passar texto puro.
E a valvula de escape: praticamente tudo e gerado, e o que nao tem construcao
automatica vira SQL explicito.

A TRANSAÇÃO (BEGIN / COMMIT)
Repare no SQL gerado: abre BEGIN; e fecha COMMIT;. Tudo numa transacao so.
O Postgres permite DDL transacional, entao se a 4a tabela de 5 falhar,
NADA e criado: volta tudo como estava. No SQL Editor do Supabase cada comando
e solto; um erro no meio deixa o banco pela metade, que e o tipo de sujeira
que nao se enxerga depois.

A MEMORIA (alembic_version)
No SQL gerado aparecem duas linhas de controle:

    INSERT INTO alembic_version (version_num) VALUES ('0001_baseline')
    UPDATE alembic_version SET version_num='0002_rls' ...

O Alembic grava a revisao no proprio banco a cada passo. E esse controle que
torna o upgrade seguro para repetir: rodando de novo, ele le '0002_rls', ve
que a head tambem e '0002_rls', e nao faz nada.

O CAMINHO INVERSO (--autogenerate)
Ate aqui o fluxo foi models -> SQL -> banco. O --autogenerate faz o oposto:

    database/models.py
         |
         +- 1. le o que o BANCO tem (information_schema)
         +- 2. le o que o CODIGO tem (Base.metadata, dos models)
         +- 3. compara os dois
         +- 4. escreve a diferenca num arquivo .py novo

Ou seja: ele LE O BANCO para descobrir o que falta e escreve o op.add_column()
por voce. (Por isso ele precisa do banco no ar: sem banco nao ha com o que
comparar.)

VER SEM APLICAR NADA
Para ver o SQL que SERIA executado, sem conectar no banco:

    alembic upgrade head --sql

Este comando e seguro e util: ele mostra exatamente o que o upgrade faria.
Para ver os dois lados (subir e descer) sem risco nenhum:

    alembic upgrade head --sql
    alembic downgrade 0002_rls:base --sql

E o SQL que o projeto gerou de verdade ao criar as tabelas (resumido):

    CREATE TABLE "Usuarios" (
        id SERIAL NOT NULL, nome VARCHAR(100) NOT NULL,
        email VARCHAR(150) NOT NULL, senha_hash VARCHAR(255) NOT NULL,
        PRIMARY KEY (id), UNIQUE (email)
    );
    CREATE TABLE "Consultas" (
        id SERIAL NOT NULL, paciente_id INTEGER,
        data TIMESTAMP WITHOUT TIME ZONE, valor NUMERIC(10, 2),
        compareceu INTEGER DEFAULT 0, pago BOOLEAN DEFAULT false,
        duracao INTEGER DEFAULT 30 NOT NULL, ...
    );
    CREATE INDEX idx_consultas_usuario ON "Consultas" (usuario_id, data);
    ALTER TABLE "Consultas" ENABLE ROW LEVEL SECURITY;
    ...


2.2 O APP NAO USA TRANSACAO (AUTOCOMMIT) E O WARNING QUE APARECEU
================================================================================

A secao anterior mostrou um BEGIN e um COMMIT no SQL. Isso e do ALEMBIC, que
abre a propria conexao (migrations/env.py) e roda cada revisao dentro de uma
transacao de verdade: se a 4a tabela de 5 falhar, nada e criado.

O APP e diferente. A engine do app (database/connection.py) nasce com
isolation_level="AUTOCOMMIT": cada statement e confirmado pelo servidor na
hora, sem BEGIN nem COMMIT. O motivo e o custo - o Supabase e remoto (RTT de
~15 ms na regiao sa-east-1) e uma transacao obrigaria o app a pagar 2 ida-e-
volta extras em CADA tela, so para ler.

O QUE O WARNING ERA
Com autocommit nao existe transacao aberta, mas o SQLAlchemy continua
chamando o commit do driver a cada db.commit() (sao 18 lugares no app) e o
pg8000 envia "COMMIT" sem olhar se existe transacao. O Postgres responde:

    WARNING:  there is no transaction in progress

e o log do Supabase enche de aviso a cada gravacao. (O ROLLBACK do
Session.close() NAO era problema: o proprio pg8000 so envia rollback quando ha
transacao em andamento.)

A CORRECAO
Em vez de abrir transacao de verdade (5x mais lento), o commit vira no-op
enquanto o autocommit estiver ligado. Em database/connection.py:

    def _anular_commit_spurio(dbapi_connection, connection_record):
        if getattr(dbapi_connection, "autocommit", False):
            dbapi_connection.commit = _nada

    event.listen(engine, "connect", _anular_commit_spurio)

O statement ja foi confirmado pelo servidor no autocommit, entao dispensar o
COMMIT nao perde nada. A engine tambem recebe skip_autocommit_rollback=True
para o ROLLBACK nao ser enviado na devolucao da conexao ao pool.

O QUE MUDOU NA PRATICA
Medido no Supabase (sa-east-1, mediana de 10 rodadas, banco com pool quente):

    operacao                    antes      depois   sem autocommit
    leitura (1 sessao)          13,5 ms    14,0 ms      77,4 ms
    Agenda (2 leituras)         23,3 ms    24,3 ms     135,2 ms
    gravacao (add + commit)     90,6 ms    47,3 ms      97,9 ms

Ou seja: o aviso some (0 warnings contados direto do servidor) sem perder
velocidade, e a gravacao ate fica mais rapida porque deixa de gastar uma
ida-e-volta com um COMMIT que nao confirmava nada.

COMO CONFERIR
    - No painel do Supabase, em Logs, o aviso "there is no transaction in
      progress" nao aparece mais.
    - No codigo, o commit e contagem zero; o INSERT continua gravado porque o
      autocommit ja o confirmou.
    - Os testes de database/connection.py cobrem o comportamento: com autocommit
      o commit e anulado; sem autocommit ele volta a valer.

REGRA PARA O FUTURO
Nada no app usa engine.begin() nem db.begin(), e nenhuma funcao grava mais de
uma linha por transacao - por isso autocommit e seguro aqui. Se um dia uma
tela precisar de transacao de verdade (gravar varias linhas e poder
desfazer), o caminho e engine.begin() com o autocommit desligado. O patch
acima e condicionado ao autocommit, entao nao atrapalha esse caso: com
transacao explicita o commit volta a ser enviado.


3. ONDE ESTA TUDO ISSO NO PROJETO
================================================================================

    alembic.ini                        configuracao geral
    migrations/README                  passo a passo curto (so os comandos)
    migrations/env.py                  ponte: pega a URL do banco do .env
    migrations/script.py.mako          modelo dos arquivos de revisao
    migrations/versions/0001_baseline.py
                                       revisao 1: cria as 5 tabelas
    migrations/versions/0002_rls.py
                                       revisao 2: liga a seguranca (RLS)

As tabelas tem nome com maiuscula, entao no SQL vao entre aspas:
    "Usuarios"   "Pacientes"   "Consultas"   "Orcamentos"   "Tratamentos"

Regra do projeto: o schema se muda em database/models.py. NUNCA editar tabela
direto no SQL Editor do Supabase, senao banco e codigo ficam diferentes.


4. OS COMANDOS
================================================================================

Todos rodam na raiz do projeto, com a venv ativa (.venv\Scripts\activate):

    alembic upgrade head
        Aplica no banco tudo que ainda falta. Cria as tabelas se o banco for
        novo. Se ja esta em dia, nao faz nada. ESSE E O COMANDO SEGURO.

    alembic current
        Mostra em qual revisao o banco esta. Ex.: "0002_rls (head)".

    alembic check
        Compara o banco com os models e avisa se ha diferenca. Nao escreve
        nada no banco. Serve para descobrir se alguem mexeu no banco na mao.

    alembic history
        Lista o historico de revisoes (o que foi criado e quando).

    alembic revision --autogenerate -m "descricao"
        Compara os models com o banco e gera o arquivo da mudanca.
        NAO aplica no banco. Leia o arquivo gerado antes de seguir.

    alembic downgrade -1
        Desfaz a ultima revisao. CUIDADO: se a revisao criou uma tabela,
        voltar um passo APAGA essa tabela e os dados que estavam nela.

    alembic upgrade head --sql
        So imprime o SQL que seria executado, sem conectar no banco.
    alembic upgrade head --sql | alembic downgrade base --sql
        Serve so para conferir os dois lados sem risco nenhum.


5. QUANDO USAR CADA UM
================================================================================

  Banco novo (projeto recem-criado no Supabase)
      1. colocar a DATABASE_URL do projeto novo no .env
      2. conferir a regiao/host no painel do Supabase
      3. alembic upgrade head      -> cria as 5 tabelas + RLS
      4. abrir o app e criar o usuario pela tela de login

  Banco antigo que JA tem as tabelas e nunca usou Alembic
      alembic stamp head
      -> so marca "este banco ja esta em dia". NAO cria tabela nenhuma.
      Use quando o banco foi montado a mao e voce nao quer recriar.

  Mudar o formato (adicionar coluna, criar indice, etc.)
      ver secao 6 abaixo

  Ficar de olho se tudo esta certo
      alembic current  +  alembic check


6. COMO MUDAR O FORMATO DO BANCO (EXEMPLO: ADICIONAR UMA COLUNA)
================================================================================

Exemplo real: voce quer um campo "observacao" na consulta.

  Passo 1 - edite database/models.py, dentro de class Consulta:
      observacao = Column(String(500))

  Passo 2 - gere a revisao (ainda nao mexe no banco):
      alembic revision --autogenerate -m "add observacao em consultas"

  Passo 3 - ABRA o arquivo gerado em migrations/versions/ e leia. Deve ter um
      op.add_column(). Se aparecer qualquer coisa estranha (drop de coluna,
      mudanca de tipo que voce nao pediu), apague o arquivo e arrume o model.

  Passo 4 - aplique:
      alembic upgrade head

  Passo 5 - confira:
      alembic check      -> tem que responder "No new upgrade operations"

Nesses 5 passos nao se abre o SQL Editor, nao se escreve SQL a mao e nao da
para o banco e o codigo ficarem diferentes.

Detalhe importante: o --autogenerate precisa que o banco esteja no ar para
fazer a comparacao. Se o Supabase estiver fora do ar, a revisao teria de ser
escrita a mao no arquivo gerado.


7. COMO SABER SE TUDO ESTA CERTO
================================================================================

    alembic current   ->  deve mostrar 0002_rls (head)
    alembic check     ->  deve mostrar "No new upgrade operations detected"

Se o check reclamar, normalmente e uma destas situacoes:
  - voce mudou models.py e ainda nao gerou/aplicou a revisao (o mais comum)
  - voce editou uma tabela direto no SQL Editor do Supabase
  - o .env aponta para outro projeto (ou a senha esta errada)


8. O QUE O ALEMBIC NAO FAZ
================================================================================

  - Nao mexe nos seus dados. Ele so cria/altera tabelas.
  - Nao e backup. Para backup, o caminho e o do proprio Supabase.
  - Nao controla o login nem o filtro por usuario (usuario_id). Isso e o app.
  - Nao controla o RLS sozinho: o RLS precisa de uma revisao propria porque o
    Alembic nao enxerga isso. No projeto, quem liga o RLS e a revisao 0002_rls.
  - Nao valida regra de negocio. Nenhum comando impede voce de criar schema
    errado; ele so garante que banco e codigo batem entre si.


9. CUIDADOS
================================================================================

  - upgrade head e seguro: cria o que falta, nunca apaga dado.
  - downgrade APAGA. Nunca rode por curiosidade para "ver o que acontece".
  - Para o Alembic, o usuario e o dono das tabelas (o app conecta como
    postgres), entao as politicas de RLS do banco nao bloqueiam o app.
  - O .env tem a senha do banco e nunca deve ir para o git. O migrations/ e o
    alembic.ini DEVEM ir para o git (sao o historico do banco).
  - Depois de mexer no schema, rode a suite de testes:
        python -m pytest -q


10. PERGUNTAS FREQUENTES
================================================================================

  P: Rodar "Criar tabelas" de novo apaga meu banco?
  R: Nao. "upgrade head" so aplica o que falta. Se ja estiver em dia, ele
     responde que nao ha nada a fazer e nao mexe em nada.

  P: Posso trocar de projeto do Supabase (de regiao)?
  R: Sim. Troque a DATABASE_URL no .env e rode "alembic upgrade head" no
     projeto novo. Os dados NAO vem junto: migracao de dado e outra coisa
     (o SQL Server antigo exportava com o script exportar_dados.py).

  P: O Alembic roda sozinho quando o app abre?
  R: Nao. Ele roda so quando voce chama um comando. O app nao mexe no formato
     do banco em momento nenhum.

  P: E se eu criar uma tabela na mao no Supabase e o app reclamar?
  R: Provavelmente voce criou fora do models.py. O certo e remover a tabela e
     refazer pelo caminho Alembic, para o codigo saber que ela existe.

  P: Preciso do Alembic para usar o app no dia a dia?
  R: Nao. So quando mudar o formato do banco. Para usar o app, e so abrir o
     python app.py normalmente.

  P: O Alembic precisa do SQLAlchemy para funcionar?
  R: Sim, e nao como opcao. O proprio pacote declara SQLAlchemy>=2.0 como
     dependencia obrigatoria. Vale separar as tres pecas, porque elas fazem
     coisas diferentes:
        SQLAlchemy  -> o tradutor. Entende o schema e escreve o SQL do banco
        pg8000      -> o telefone. Leva o texto ate o Supabase
        Alembic     -> o contador. Lembra o que ja foi aplicado
     E por isso que o Alembic depende do SQLAlchemy: o passo 6 da secao 2.1
     (traduzir sa.Integer() em SERIAL) so existe porque o SQLAlchemy conhece os
     dialetos. Sem ele o Alembic perderia a parte mais valiosa.
     Nada de instalacao extra: sqlalchemy, pg8000 e alembic ja estao no
     requirements.txt, e o Alembic roda no mesmo Python do app, usando o mesmo
     engine (migrations/env.py importa de database/connection.py).
